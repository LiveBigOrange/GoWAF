## 修复1: ACME 证书配置窗口超时不关闭

### 问题描述
在证书管理中添加域名并点击"保存并应用"后，ACME 自动证书配置窗口不会自动关闭。后台日志显示证书申请成功，但前端因请求超时未收到响应。

### 根因
后端 `APIACMEConfig` 同步执行 `deps.ACMEManager.UpdateConfig()`，该方法内部会向 Let's Encrypt 申请证书，耗时约 32 秒。前端 fetch 请求超时（浏览器默认约 30 秒），导致未执行 `closeACMEConfig()` 关闭窗口逻辑。

### 修复
**文件**: `internal/web/handler/acme.go:71`

将同步调用改为异步 goroutine 执行，API 立即返回响应：

```go
// 修复前
deps.ACMEManager.UpdateConfig(email, validDomains)

// 修复后
go deps.ACMEManager.UpdateConfig(email, validDomains)
```

同时更新响应消息为 `"ACME配置已更新，证书申请已在后台启动"`。

### 影响范围
- ACME 证书配置保存接口
- 证书申请改为后台异步执行，可在日志中查看进度

## 修复2: 系统设置中修改密码成功后不跳转登录页

### 问题描述
在"全部设置 > 密钥与工具 > 修改密码"中修改密码，提示修改成功但不会退出到登录窗口。

### 根因
`config_system.js` 中 `changePassword()` 函数修改成功后仅调用 `closeModal()` 关闭模态框，未跳转到登录页。密码修改后 session 已失效，应强制重新登录。

### 修复
**文件**: `internal/web/static/js/config_system.js:521-523`

```javascript
// 修复前
if (resp.success) { showToast('success','密码已修改'); closeModal(); }

// 修复后
if (resp.success) {
    showToast('success','密码已修改，即将重新登录');
    setTimeout(function() { window.location.href = '/logout'; }, 1500);
}
```

### 影响范围
- 系统设置页面的修改密码功能
- 修改成功后 1.5 秒自动跳转 `/logout`，清除 session 并重定向到登录页

## 修复3: 独立修改密码页面缺少 CSRF Token

### 问题描述
修改密码独立页面（`/change-password`）的 fetch 请求未传递 `X-CSRF-Token` 请求头，可能导致请求被 CSRF 中间件拦截。

### 根因
`change_password.html` 中 `submitPassword()` 函数的 fetch 请求 headers 仅设置了 `Content-Type`，未包含 CSRF Token。

### 修复
**文件**: `internal/web/templates/change_password.html:464-470`

```javascript
// 修复前
fetch('/api/admin/change-password', {
    method: 'POST',
    headers: {
        'Content-Type': 'application/json'
    },
    body: JSON.stringify({ old_password: oldPwd, new_password: newPwd })
})

// 修复后
var csrfToken = document.querySelector('meta[name="csrf-token"]');
var headers = {
    'Content-Type': 'application/json'
};
if (csrfToken) {
    headers['X-CSRF-Token'] = csrfToken.content;
}

fetch('/api/admin/change-password', {
    method: 'POST',
    headers: headers,
    body: JSON.stringify({ old_password: oldPwd, new_password: newPwd })
})
```

### 影响范围
- 独立修改密码页面（`/change-password`）
- 与系统设置页面中的修改密码保持一致，均传递 CSRF Token

## 修复4: 后端服务配置 HTTPS 协议时 502 错误

### 问题描述
WAF 代理服务配置了监听 HTTPS 443 端口，后端服务配置为 HTTPS 协议转发到 nginx 8443 端口（nginx 配置了 SSL 证书），通过 WAF 访问报 502 错误。

### 根因
WAF 使用 `https://127.0.0.1:8443` 连接后端 nginx，但 nginx 的 SSL 证书颁发给域名（如 `www.yzn123.cc`），连接地址是 IP 地址。Go 的 `http.Transport` 默认验证证书域名与连接地址是否匹配，IP ≠ 域名，TLS 握手失败，导致 502。

### 修复
**文件**: `internal/proxy/proxy.go:91-93`

在反向代理的 Transport 中添加 `TLSClientConfig`，跳过内部连接的证书验证：

```go
// 修复前
Transport: &http.Transport{
    MaxIdleConns:          500,
    MaxIdleConnsPerHost:   100,
    IdleConnTimeout:       90 * time.Second,
    ResponseHeaderTimeout: 30 * time.Second,
    ExpectContinueTimeout: 1 * time.Second,
    DisableCompression:    cfg.Performance.DisableCompression,
    ForceAttemptHTTP2:     true,
}

// 修复后
Transport: &http.Transport{
    MaxIdleConns:          500,
    MaxIdleConnsPerHost:   100,
    IdleConnTimeout:       90 * time.Second,
    ResponseHeaderTimeout: 30 * time.Second,
    ExpectContinueTimeout: 1 * time.Second,
    DisableCompression:    cfg.Performance.DisableCompression,
    ForceAttemptHTTP2:     true,
    TLSClientConfig: &tls.Config{
        InsecureSkipVerify: true,
    },
}
```

同时在 `proxy.go` 的 import 中添加 `"crypto/tls"`。

### 安全性说明
- WAF 与后端通常在同一服务器（`127.0.0.1`）或内部可信网络
- 本地回环地址无法被外部劫持，跳过验证不影响整体安全
- WAF 本身已使用有效证书（ACME）处理外部连接

### 影响范围
- 所有通过 HTTPS 协议转发到后端的请求
- 解决后端使用 IP 地址但证书颁发给域名时的 502 错误

## 修复5: 健康检查对 HTTPS 后端误判不健康

### 问题描述
与修复4 同源。当后端配置为 HTTPS 协议且地址使用 IP 时，健康检查也会因证书域名不匹配而连接失败，导致后端被标记为不健康，进而 502 错误。

### 根因
`health.go` 中 `NewHealthChecker` 创建的 HTTP 客户端仅设置了 `MinVersion: TLS1.2`，未设置 `InsecureSkipVerify`，证书验证逻辑与代理转发一致，同样会因域名不匹配而失败。

### 修复
**文件**: `internal/backend/health.go:39-41`

```go
// 修复前
TLSClientConfig: &tls.Config{
    MinVersion: tls.VersionTLS12,
}

// 修复后
TLSClientConfig: &tls.Config{
    MinVersion:         tls.VersionTLS12,
    InsecureSkipVerify: true,
}
```

### 影响范围
- HTTPS 后端服务的健康检查
- 确保健康检查与代理转发使用一致的证书验证策略

## 修复6: 添加 X-Forwarded-Host 请求头

### 问题描述
WAF 转发请求到后端时，已设置 `X-Real-IP`、`X-Forwarded-For`、`X-Forwarded-Proto`，但未设置 `X-Forwarded-Host`。后端应用无法通过标准头获取原始域名，可能导致重定向 URL、Cookie 域名等生成错误。

### 背景
多个 WAF 域名配置可能转发到同一个后端地址和端口，后端 nginx 通过 `server_name` 区分流量。WAF 保留了原始 Host 头（`req.Host` 未修改），nginx 可以根据 Host 头匹配 `server_name`。但后端应用（如 Halo）可能需要 `X-Forwarded-Host` 来获取原始域名。

### 修复
**文件**: `internal/proxy/forward.go:117-119`

```go
// 新增
if originalHost := req.Host; originalHost != "" {
    req.Header.Set("X-Forwarded-Host", originalHost)
}
```

### 影响范围
- 所有转发到后端的请求
- 后端应用可通过 `X-Forwarded-Host` 获取原始域名
- 与 `X-Real-IP`、`X-Forwarded-For`、`X-Forwarded-Proto` 形成完整的转发头链
